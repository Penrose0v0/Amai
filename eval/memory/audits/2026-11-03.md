## 标注口径

逐条审计每一条新写入的有效记忆，标为以下四类之一：

| 标注 | 含义 |
|---|---|
| ✅ 正确 | 内容正确，分区、小节、主体正确，依据类型合理，有长期价值 |
| ❌ 事实错误 | 内容与依据不符：夸大、把推断说成事实、把阅读当成计划、已过时却仍然有效 |
| ↪ 错误归属 | 写进了错误的分区或小节，或者把他人的数据当成用户本人的 |
| ♻ 低价值冗余 | 内容不算错，但属于一次性、短期的流水账，或在另一个分区逐字重复 |

指标定义：

| 指标 | 定义 |
|---|---|
| Precision | ✅ 条数 / 写入总数 |
| 错误归属率 | ↪ 条数 / 写入总数 |
| 冗余率 | ♻ 条数 / 写入总数 |
| Recall | 期望事实中，以 ✅ 条目形式出现在正确分区的比例 |
| 锚点召回 | 只要关键词命中就算找到（评测工具自动计算），列出来作对照 |

关于"上一轮的 17 条"：上一轮报告的 17 条记忆当时没有保存逐条内容，无法回溯。这里用相同的提示词与规则重跑了开发场景，Opus 恰好也写入了 17 条，审计的是这一次的结果。

## 结论

### Opus

- 没有事实错误，没有写入任何不应出现的内容（0/36），召回率 94%。
- 主要问题是跨分区重复：7 条非 ✅ 中有 5 条是同一句话在 Work、Goals、Health 之间重复，另有 2 条是短期安排或短期状态。
- 冗余率 15%、错误归属率 12% 主要都来自这类重复。

### Gemma（e4b，4 bit）

结构化 JSON 全部合格，没有不合格输出，但语义上不能用于整理：
- 提出的操作有 56% 被代码拒绝。常见原因：把非工作内容加进 Work 且不填项目；Goals 小节名不对；金额不填币种和日期；不填数据主体。
- 主体判断很差：父亲的手术、猫的病被写进了用户的 Health。
- 把阅读当成计划；出现夸大和过时信息。
- Precision 47%，Recall 39%。

代码校验拦下了大部分违规操作，但能拦的只有格式和依据，拦不住"主体是谁""阅读不等于计划"这类语义错误。

## 评测发现的代码问题（不在 held-out 上调优，记录待修）

1. **用户陈述的覆盖率可以被专名带过门槛。** 条目和笔记都含有同一个英文名（如 Orbit、Lumen）时，二元组覆盖率偏高，加了推测的条目也可能被记为 stated。
2. **引用 F 的条目被整体记为 observed。** F 只能证明"使用了某应用"，但目前条目只要提到应用名，就会整体被记为 observed（例如 Gemma 第 7 条，阅读内容其实是推断）。应改为：只有当条目内容不超出"时段 + 应用"时才记为 observed，否则按推断处理。
3. **跨分区重复没有防护。** 同一条用户陈述被写进多个分区时，代码不会拦截。
4. **锚点评分有误报。** 评测工具按关键词判断"新旧同时有效"会误报，例如"曾担心…；现在正常"这类更新。正式指标以人工审计为准。
