# 0012 · 记忆检索：按 token 预算选取、修正融合与日期解析

- 状态：**Accepted**（2026-11-21 用户要求实现）。取代 ADR-0011 中"检索结果最多 6 条、整天时间线按 1800 字符截断、整段 5000 字符"的部分；ADR-0011 的其余内容（固定流水线、混合检索的结构、预填充）不变。
- 日期：2026-11-21
- **性能结论待定**：下面的数字来自临时 GT（出题时的种子证据），只用于诊断。结论以 30 道题的人工 GT 为准（`docs/qa-eval.md`「检索评测」）。

## 背景

真实记忆上的检索评测（`amai-memory qa-eval retrieval`，临时 GT，67 题）里，问答实际使用的 `MemoryRecall` 只有 61% 的题拿全了所需证据，平均只用了 684 token。漏掉的 27 个信息点：

| 原因 | 个数 |
|---|---|
| 混合检索能找到，但排在第 6 名之后 | 10 |
| 按日期取出的整天时间线超过 1800 字符被截断 | 8 |
| 混合检索前 50 名都没有（其中 5 个纯关键词能找到） | 5 |
| 问题写了那天，日期写法没被认出 | 4 |

## 决策

### 一、按 token 预算选取（`MemoryRecall`）

候选：混合检索取 50 条（`MemoryAPI` 的上限）；问题提到的每一天（最多 3 天）的日终摘要与每个片段；日期区间里每天的概要。

按优先级装入，直到预算（默认 4096 token，`AssistantSession.Configuration.memoryTokenBudget`）用完：

1. 提到的那几天的日终摘要、日期区间里每天的概要；
2. 按相关度排序的条目：混合检索的结果，与"这一天里按问题排出的片段"（对那一天做一次限定日期的检索，`MemoryAPI.search(days:)`）一起按得分从高到低；
3. 那几天里剩下的片段，按时间顺序。

一天没有放全时注明"还有 N 条没放"，之前轮次给过的也注明条数，模型知道它看到的不是全部。

**去重**：提到的那天里的检索命中只出现在那天的时间线里（不再在"检索结果"里重复）；归一化后文字相同的检索结果只放一次；同一段对话里给过的内容按**条目**记录（原来按整天），所以追问"那天还做了什么"能拿到第一轮没放下的片段。

**相对门槛**：检索结果低于第一名得分的 0.5 倍就不放。第一名总会保留，所以不是"无关问题什么都不给"的绝对门槛（按用户要求，暂不加）。临时 GT 上相关结果的得分最低是第一名的 0.57 倍：0.5 不会裁掉它们，但余量不大，且是在同一批题上看的。

token 估算与索引切块相同（汉字每字 1，其余每 4 字符 1）。

### 二、融合：关键词候选补上真实的语义得分（`MemoryIndex.search`）

向量一路只把"高于索引平均 1.5 个标准差"的前若干块作为候选；关键词命中、却不在其中的块，原来的语义得分按 0 计，融合得分最多只有关键词权重 0.3，过不了最低分 0.30——关键词命中得再好也会被丢掉。现在给这些块补上它们真实的（线性换算后的）语义得分再融合。门槛、权重、校准方式都不变。

### 三、日期解析（`DateMentions`）

增加：`N 天前 / N天之前 / N days ago / N日前`；英文月份（`November 11th`、`Nov 6, 2026`、`the 6th of November`）；日文星期（`先週の金曜日`、`今週の月曜`、`金曜日`）；英文星期（`last Friday`、`this Monday`、`on Wednesday`）。"上 / 先週 / last"指上一个自然周的那天，"这 / 今週 / this"指本周的那天，没有修饰取最近的那一个。点明了星期几时不再同时当作一整周。

### 四、MMR 的计算方式

"与已选结果的最大相似度"改为每选中一条只更新一次，结果与原来逐轮重算完全相同（有测试），取 50 条时快得多（原来取 50 条约 300–700 毫秒）。

## 诊断结果（临时 GT，67 题，不作为最终结论）

| | 证据召回 | 所需证据全部召回 | 平均 token | 记忆检索 p50 / p90 |
|---|---|---|---|---|
| 优化前 | 65.7% | 61.2% | 684 | 34 / 135 毫秒 |
| 优化后（4K） | 94.0% | 92.5% | 2522 | 64 / 97 毫秒 |
| 优化后（8K） | 94.0% | 92.5% | 2581 | 63 / 94 毫秒 |

剩下 5 个漏掉的信息点：4 个混合检索前 50 名都没有，1 个被日期范围筛掉。8K 与 4K 几乎相同：预算在这批题上基本不是瓶颈。合成记忆库的 26 题检索评测（`RetrievalEvalTests`）结果不变（前 6 条命中 25 个）。

## 取舍与风险

- **提示词变长**：平均从约 700 增加到约 2500 token。本地模型的预填充随之增加（Gemma 4 E4B 上每 1000 token 约 0.4 秒），这部分在提交之后，算在首字延迟里。回答质量是否因此变好或被无关条目干扰，本 ADR 没有测（用户要求暂不评测回答）。
- **无法回答的问题带上更多无关记忆**：9 道"记忆里没有的事"平均从 400 增加到 2400 token。没有加分数门槛（用户要求）；以后要处理时，评测里第一名得分的 AUROC（0.97）说明一个门槛是可行的。
- **混合检索变慢**：取 50 条约 55 毫秒（原来取 6 条约 22 毫秒）；整个记忆检索一步 p50 约 64 毫秒。
- 相对门槛 0.5 与预算 4096 都是在同一批真实问题的临时 GT 上看过的，存在过拟合的可能；人工 GT 的 30 道题也取自这一批。
- 预算按估算的 token 计，与模型的实际分词有出入。

## 备选方案

- **只把 6 条改大**（例如 20 条）：简单，但条数与长度无关，长条目多时仍会撑爆、短条目时又浪费；整天时间线的截断也还在。未采用。
- **整天时间线只提高字符上限**：真实的一天有 30 多个片段，按时间顺序截断时，与问题相关的那条可能在任何位置。改为按问题给当天的片段排序。
- **RRF 融合**：ADR-0011 已因没有绝对分数而不用；这里只修正"缺失的语义分当 0"这一处。
- **不可回答问题的分数门槛**：用户要求暂不加入。
