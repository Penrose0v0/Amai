# 0011 · 问答管线：后端检索记忆、混合检索、面板唤出时预填充

- 状态：**Accepted**（2026-11-18 用户确定方向并要求实现）。检索结果的条数（6 条）与时间线的字符截断已由 ADR-0012 改为按 token 预算选取。取代 ADR-0010 中"Agent 循环 + 记忆工具"的部分：普通问答不再经过工具调用。ADR-0010 的其余内容（模块划分、统一对话接口、交互式屏幕读取、快速操作、权限与云端边界）不变。
- 日期：2026-11-18

## 背景

ADR-0010 把记忆做成三个工具，由模型自己决定何时调用。实测的问题：

- Gemma 4 E4B 调用工具不稳定：会把"某天做了什么"当成关键词去搜，追问时答"没有记录"。为此加的缓解（提示词强制先调工具、检索工具识别日期）是在工具层给模型兜底。
- 没有工具能力的来源（Claude Code）走另一条"预检索"路径，同一件事有两套实现。
- 记忆检索是 section 粒度的全文索引，把整个问题当成一个短语去匹配：自然语言的问句基本搜不到东西。
- 截图、OCR、上下文收集都在用户提交之后才开始，窗口 OCR 约 1.2 秒，全部算在首字延迟里。

用户确定的要求：

1. 后端负责记忆检索与上下文组装，再调用模型；普通问答不依赖工具调用，也不为读记忆引入 Agent 循环或 MCP 桥接。保留多模型、流式、KV cache，保留今后扩展 Agent 的可能。
2. 记忆检索升级为关键词 + 向量的混合检索，参考 OpenClaw 的实际实现；在现有 Memory API 与 SQLite 索引上做。
3. 面板唤出时立即 OCR、并行准备记忆与上下文、尽可能提前做 prompt prefill；先确认推理后端是否真的支持增量 prefill。

## 参考项目的实际做法

**OpenClaw**（读的是源码，`extensions/memory-core`、`packages/memory-host-sdk`、`src/agents/memory-search.ts`）：

- 按行切块，约 400 token、重叠 80；SQLite 里一张块表、FTS5 表、sqlite-vec 表、按（provider，model，内容哈希）的向量缓存。
- 关键词：先 AND 查询，没有结果再 OR 并做查询扩展（去停用词，汉字切成单字与 bigram）。BM25 折算：`rank < 0 ? -rank / (1 - rank) : 1 / (1 + rank)`；再按"问题里的词命中了多少"加成。
- 向量：默认 OpenAI 的 embedding，本地可选 llama.cpp 的 embeddinggemma-300m；没有 provider 时只用关键词。
- 融合是加权求和（向量 0.7、关键词 0.3），不是 RRF；每路取 4 倍候选，最低 0.35 分，最多 6 条；然后时间衰减（半衰期 30 天，非日期文件不衰减）与 MMR（λ 0.7，相似度是词集合的 Jaccard）。
- 结果默认通过 `memory_search` 工具给模型；自动注入是另一个插件，用一个子 Agent 检索后总结成不超过 220 字符的一句话再放进提示词。

**Atd**（`apps/macos` 是 Swift 外壳，推理全部经 Pi SDK 走 HTTP）：

- 面板先显示，选区在后台按"按下快捷键时的前台进程"读取，每个辅助功能调用都有时间上限。
- OCR 用 Apple Vision，在用户确认截图区域时与图片编码并行，最多等 3 秒。
- 动态上下文作为一条消息插在"历史之后、当前问题之前"，system 保持不变以稳住缓存前缀。
- **没有**任何提交前的预热或 prefill，没有本地推理，也没有 KV cache 处理。记忆靠工具调用。

所以预填充这部分没有现成做法可参考，取决于我们自己的 MLX 运行时。

## 决策

### 一、问答是一条固定的流水线

```text
读屏幕上下文 ─┐
              ├→ 组装提示词 → ChatModel 流式生成
检索记忆 ─────┘
```

- `AssistantSession`（原 `AgentSession`）：没有循环，每轮只调用模型一次，请求里不带工具定义。
- `MemoryRecall`：调用模型之前由后端检索。两条路并行：
  - 问题里的日期（"昨天""11 月 6 日""上周三""过去 5 天"，中英日）由规则解析，直接取那几天的时间线；
  - 其余用问题做一次混合检索，取前 6 条。
  - 问题限定了日期时，检索结果也只保留那几天的；追问里的"那天"沿用上一个问题的日期。
  - 同一段对话里给过的内容不重复给（它们还在历史里）。
- 可读分区仍由 `MemoryAPI` 的 `MemoryAccess` 决定，本地与云端相同。
- 回答下方的来源 = 这一轮实际放进提示词的记忆。
- 删除：`MemoryTools`、`look_at_screen` 工具、工具循环、"无工具模型的预检索"分支、检索工具里识别日期的补丁。截图只在用户打开"带上屏幕"时附带。
- 保留给今后的 Agent：`ChatModel` 的工具调用契约、四个云端来源与本地 MLX 的工具调用实现（有测试）都还在。要加 Agent 时在这条流水线之上加一个循环，普通问答不受影响。

与 OpenClaw 自动注入的差异：它再过一遍模型做总结，我们直接放检索到的条目。原因是我们的块本来就是一条一条的短句（见下），6 条通常只有几百个字符，再调用一次模型不划算。

### 二、混合检索（`AmaiMemory`）

在现有的索引数据库里加三张表，与原来的 section 表同一次刷新；原来的 `retrieve`（记忆浏览窗口的字面查找）不变。

- **切块**：一个条目一块（长期记忆的一条、时间线的一个片段连同它的摘要行）；小节标题（`### 项目名`）作为块的标题。没有列表的段落按约 240 token 切。不做重叠。
- **关键词**：索引前先分好词再交给 FTS5（unicode61）——拉丁字母按词、汉字 bigram、片假名整段。查询去掉疑问词和助词，各词之间是 OR，BM25 排序，折算与"命中比例"加成同 OpenClaw。
- **向量**：`TextEmbedder` 契约在 AmaiCore；实现是 `MLXTextEmbedder`（mlx-swift-lm 的 MLXEmbedders，不是新的依赖包）。向量以 BLOB 存在 SQLite，按（模型，内容哈希）存放；查询时用 Accelerate 暴力算点积。
- **融合**：OpenClaw 的加权求和与关键词折算；时间衰减只作用于 daily，并且有下限 0.6；MMR 用词集合的 Jaccard。
- **回退**：没有下载向量模型、问题向量 2 秒内没算出来、索引里还没有向量时，只用关键词。
- 向量的补算在后台优先级进行（面板唤出时触发），只算内容变了的块。

**向量模型的选择**（合成记忆库：45 天的每日记录加五个分区，26 个有标准答案的问题；数字是"前 6 条里有正确答案"）：

| 方式 | 字面问题（8） | 改写问题（14） | 跨语言问题（4） | 单次检索 |
|---|---|---|---|---|
| 仅关键词 | 8 | 4 | 0 | 不到 1 毫秒 |
| 关键词 + multilingual-e5-small | 8 | 8 | 3 | 约 5 毫秒 |
| 关键词 + Qwen3-Embedding-0.6B（4bit） | 8 | 14 | 3 | 约 17 毫秒 |

E5 那一行是选型过程中测的，当时的打分刻度与最终版略有不同（最低分 0.35），只用来比较两个模型。

选 Qwen3-Embedding-0.6B（4bit，下载约 330 MB，1024 维）。除了命中率，还因为它的相似度有可用的绝对刻度（无关内容中位数 0.29，相关内容平均 0.54）；E5 对任意两段文字都给出 0.75–0.9，没法设门槛。系统自带的 `NLContextualEmbedding` 需要系统另行下载资源，且不是为检索训练的，没有采用。

与 OpenClaw 的差异：

| | OpenClaw | Amai | 原因 |
|---|---|---|---|
| 块 | 约 400 token，重叠 80 | 一个条目一块 | 记忆文件本来就是条目；小块命中更准，注入更省 |
| 中文分词 | unicode61 + 子串匹配，OR 阶段才切 bigram | 索引时就切 bigram | 中文问句没有空格，整句当一个词什么都搜不到 |
| 关键词查询 | 先 AND 后 OR | 直接 OR | bigram 之下 AND 对问句过严 |
| 向量存储 | sqlite-vec，回退到逐行扫描 | 逐行扫描 | 几千块的量级毫秒可完成，不值得加扩展 |
| 最低分 | 0.35 | 0.30 | 评测里几个只靠语义命中的正确结果落在 0.32–0.34 |
| 时间衰减 | 无下限 | 下限 0.6 | 几个月前的事仍是用户会问的 |
| 向量得分 | 余弦相似度 | 按模型的有效区间换算，并要求高于索引平均 1.5 个标准差 | 很短很泛的问题与所有内容的相似度都偏高 |

### 三、提前准备与预填充

**推理后端是否支持增量 prefill——结论：支持，但只能追加，不能回退。**

- mlx-swift-lm 的 `TokenIterator` 可以在一份已有的 KV cache 上继续处理一段 token，构造时就完成 prefill；`ChatSession` 没有"只 prefill 不生成"的入口。
- Gemma 4 的滑动窗口层用 `RotatingKVCache`，超过窗口长度后**不能回退**（实测：历史分叉时可复用 0 个 token）。所以"先把上下文算进去，不对再退回来"行不通。

据此在 `LocalModelHost` 里加了一条**前缀缓存**路径（纯文字、不带工具的请求）：

- 自己持有 KV cache 和"缓存里依次是哪些 token"的账本。每次把完整提示词渲染成 token，与账本比较，只把多出来的部分喂给模型。因为比较的是 token 而不是消息，可以预先算进"下一条消息的开头"。
- 两份缓存：`committed`（上一轮结束时）和 `speculative`（在 `committed` 的**副本**上预填充了屏幕上下文）。预填充的内容作废时（用户换了窗口）退回 `committed`，不需要回退缓存。
- 带图片、带工具或一次性的请求仍走 `ChatSession`。

**提示词的排列**（越早确定的越靠前）：

```text
system（固定） → 历史（只追加） → <context> 屏幕上下文 → <memory> 检索到的记忆 → 问题
└────── 上一轮结束时已在缓存 ──────┘ └─ 面板唤出时预填充 ─┘ └──── 提交后才处理 ────┘
```

记忆取决于问题，所以排在屏幕上下文之后。时间写在 `<context>` 里（准备时的时间）；它不在 system 里，也不随提交时刻变化，否则前缀对不上。

**面板唤出时**（`AssistantSession.prepare`），三件事同时开始：

1. 加载模型，预填充 system 与历史；
2. 更新记忆索引，加载向量模型；
3. 读焦点，对前台窗口截图并 OCR。

屏幕上下文读好后再预填充它。用户换了应用、窗口或选区时重新准备；一轮结束后为下一轮准备。

**提交时**：再读一次屏幕做确认——画面哈希没变就复用上次的 OCR 结果（90 秒内），所以这一步只花一次截图的时间。内容相同就沿用准备好的那一份（它的 token 已在缓存里），不同则用新读的。

云端模型没有预填充，但同样受益于提前读好的屏幕上下文和稳定的前缀。

### 实测（M5 Pro，Gemma 4 E4B，合成记忆，`--assistant-check`）

同一个问题，提示词约 2240 token：

| | 直接提交 | 提前准备后提交 |
|---|---|---|
| 提交后的准备（屏幕、记忆、组装） | 1039 毫秒 | 83 毫秒 |
| 其中记忆检索 | 25 毫秒 | 23 毫秒 |
| 模型处理提示词 | 938 毫秒（2239 token） | 101 毫秒（159 token，其余 2080 已在缓存） |
| **提交到第一个字** | **2020 毫秒** | **211 毫秒** |

准备本身约 2.2 秒（OCR 约 1.1 秒，预填充约 0.5 秒），发生在用户打字的时候。模型冷加载约 3 秒，也移到了这段时间里。之后的追问首字约 200 毫秒。

## 备选方案

- **保留工具循环，只改进提示词**：小模型的问题不在提示词；没有工具能力的来源仍需要另一条路。未采用。
- **用模型把问题改写成检索词**：多一次模型调用，首字延迟翻倍。日期用规则、其余靠向量已经够用。
- **RRF 融合**：不需要校准得分，但没有绝对分数，无法判断"这个问题与记忆无关"。未采用。
- **提交时回退缓存来丢弃作废的预填充**：Gemma 的缓存不支持，见上。
- **记忆也预先检索**（按选区或窗口标题猜）：猜错的内容会留在缓存里，而检索本身只要 20 毫秒。未采用。

## 取舍与风险

- 向量模型是可选下载。没有它时改写类问题的命中率明显低（上表第一行）。
- 评测用的是合成数据，26 个问题；真实记忆上的质量没有测过。门槛与权重是在这份数据上定的。
- 检索不到时不会注入任何东西，但检索到的未必相关：与记忆无关的问题（"润色这封邮件"）偶尔会带上几条沾边的条目，靠提示词让模型忽略。
- 日期解析只认明确的写法；"前阵子""国庆那几天"认不出，退回普通检索。
- 预填充按"用户会就当前屏幕提问"来做；问题与屏幕无关时，这部分计算是白做的（约 0.5 秒 GPU 时间）。
- 前缀缓存不携带模型的附加状态（部分视觉模型用它定位图片之后的 token）。目录里的 Gemma 模型不需要；手动填写的其他模型未验证。
- `speculative` 与 `committed` 同时存在时多占一份历史长度的 KV cache，生成开始时释放其中一份。
- 向量补算在后台优先级，但闸门不抢占：一批（16 块）进行中时交互式请求要等它结束，约 0.1–0.2 秒。

## 影响

- `AmaiAssistant`：`AssistantSession`、`MemoryRecall`、`DateMentions`、`ScreenLook`、`ContextBuilder`；删除 `AgentSession`、`AgentTools`。
- `AmaiMemory`：`MemoryIndex.search` / `embedPending`，索引数据库增加 `chunk`、`chunk_fts`、`embedding`（已有的索引在升级后自动重建）；`MemoryAPI.search` 改用混合检索，结果是条目粒度并带 `score`，MCP 的 `search_memory` 随之受益（MCP 进程里没有向量模型，只用关键词）。
- `AmaiInference`：`MLXTextEmbedder`；`LocalModelHost` 的前缀缓存与 `prefill`。`AmaiCore`：`TextEmbedder`、`ChatModel.prepare`。
- `AmaiPerception`：屏幕文字按画面哈希复用上次的 OCR 结果。
- 设置「助手」页增加语义检索模型的下载。
- 文档：`architecture.md`、`memory.md`、`roadmap.md`、`release.md` 同步更新。
