# Amai 记忆系统设计

> 状态：草案（2026-10-19）；目录与条目格式按 Memory Schema v1 更新（2026-11-03，ADR-0006）。描述基于 Markdown 的长期记忆层：目录结构、文件格式、写入规则、检索与整理。整合 / 遗忘等算法细节标注为"待设计"，需与用户讨论后定稿，不由 Coding Agent 单方面决定。

## 1. 设计目标

| 目标 | 含义 |
|---|---|
| Markdown 为唯一真相 | 索引、缓存、向量都可以删掉重建；Markdown 丢了就是记忆丢了 |
| 人可读可编辑 | 用户用任何编辑器打开都能看懂、能改；系统尊重用户的修改 |
| 可追溯 | 每条有价值的记忆能回溯到时间与来源（哪一天、哪个活动片段） |
| 分层 | daily 是时间流水，分区文件（work / health / finance / goals）是整合结果，general 是稳定画像；三者信息密度递增、更新频率递减 |
| 不污染 | 推断不冒充事实；高频噪音不进分区文件与 general |

## 2. 目录结构（Schema v1）

```text
memory/
├── general.md              综合档案（取代 summary.md）
├── work.md                 工作与研究，按项目分组
├── health.md
├── finance.md
├── goals.md
├── daily/
│   └── YYYY-MM-DD.md       每日记录
└── .archive/               迁移归档与回滚目录（隐藏，不参与索引与整理）
```

- 每个主要分区原则上只有一个文件；文件不存在时按需创建，系统不预建空模板。
- 分区（`MemoryCategory`：general / work / health / finance / goals / daily）是检索过滤与今后向外部 Agent 授权读取的单位。
- 用户自建的其他 Markdown 文件照常被索引，但不属于任何分区。
- 旧布局（summary.md、work/、goals/、health/、finance/）由启动时的迁移搬入（§3.6）。

## 3. 文件格式

### 3.1 通用约定

- 纯 Markdown，UTF-8，LF 换行。
- 顶部可选 YAML frontmatter，仅保存少量元数据（`updated`、`kind`），正文不依赖 frontmatter 也能阅读。
- 二级标题 `##` 作为可寻址的 section；系统按 section 更新，而不是整文件重写。
- 系统生成的条目带来源标记；用户手写的内容没有标记，系统视为 `stated`（用户陈述），**优先级高于推断**。

### 3.2 条目格式（Schema v1 已实现）

系统区块中的每条记忆是一个列表项，尾部用 HTML 注释（渲染时不可见）记录来源日期与依据类型：

```markdown
- 完成抽取层 MVP <!-- src:2026-10-19,2026-10-20 kind:inferred -->
- 博士二年级 <!-- src:2026-10-16 kind:stated -->
- 某大学研究生 <!-- src:2026-10-19 -->
```

| kind | 说明 |
|---|---|
| `observed` | 有直接观察依据（屏幕文字、焦点记录等） |
| `inferred` | 模型推断 |
| `stated` | 用户明确陈述（手写或对话） |
| `confirmed` | 用户明确确认过的信息 |
| `unknown` | 兼容状态：Schema v1 之前的条目没有记录依据；不写 `kind:`，**不视为 stated** |

- kind 表示依据，不等于真实性或置信度。
- 合并：文字（规范化后）相同且 kind 相同才合并，来源取并集；kind 不同的同文条目分开保留。
- 依据校验：整理改写已有条目时沿用原 kind；只有调用方确认存在用户陈述或确认依据时，才允许从 observed / inferred / unknown 升到 stated / confirmed。模型不能自行升级。
- 无法识别的 kind 值按 unknown 读入，条目不丢弃。

daily 时间线使用行尾 `seg:` / `conf:` / `src:` 注释（见 3.3），条目都是推断，不逐条标注 kind。

### 3.3 daily/YYYY-MM-DD.md（M3 已实现）

```markdown
# 2026-10-20

## 时间线

<!-- amai:timeline:begin · 由 Amai 根据屏幕活动自动维护，均为模型推断；区块内的修改会被覆盖，需要保留的内容请写在区块外 -->
- 12:31–12:37 浏览项目文件与日程安排 <!-- seg:018B32B8-… conf:0.88 src:mlx:gemma-4-e4b-it-4bit -->
  在编辑器中浏览 Amai 项目文件，并切换到浏览器查看邮件和日历。
- 14:02–14:20 〔低置信〕使用 Xcode <!-- seg:… conf:0.30 src:fallback:metadata -->
<!-- amai:timeline:end -->

## 我的笔记
（区块外的内容由用户自由编写，系统永不修改）
```

规则（2026-10-20 用户确认）：

- **系统管理区块**：两条 HTML 注释之间完全由系统生成，每次按当天全部活动片段整体重渲染（幂等）；区块外的内容系统不读不改。
- **稳定 ID**：每行以 `seg:<UUID>` 对应一个 ActivitySegment，片段跨窗口延续时 ID 不变，只更新时间与文字。
- **片段筛选**：正常片段与低置信度片段写入，低置信度（置信度低于 0.5 或兜底片段）在标题前加〔低置信〕；空闲与隐私跳过片段不写入。
- **全部为推断**：时间线条目都是模型推断，因此不逐行标注 kind，只在开始标记中说明；`conf` 与 `src` 记录置信度与来源。
- **区块缺失与损坏**：用户删掉整个区块时，系统在文末追加新的"时间线"小节；只剩一条标记或顺序颠倒时拒绝写入并报错，避免误删用户内容。
- **无内容不建文件**：当天没有可写入的片段时不创建 daily 文件。
- 写入前对标题与摘要再做一次凭据脱敏，并去掉会破坏区块结构的换行与注释符号。

摘要、工作要点、状态等其他小节由 M4 的日终整理生成，设计待定。

### 3.4 分区文件（Schema v1）

每个分区文件是半结构化 Markdown：

```markdown
# Work

（用户可以在任意位置自由编写，系统永不改写）

## Amai 整理的记忆

<!-- amai:memory:begin · 由 Amai 根据每日记录自动维护；… -->
### Amai
- 完成抽取层 MVP <!-- src:2026-10-19 kind:inferred -->
- 〔决策〕记忆以 Markdown 为唯一事实来源 <!-- src:2026-10-20 kind:inferred -->
### MAWS-Eval
- 搭建评测框架 <!-- src:2026-10-21 -->
<!-- amai:memory:end -->
```

推荐结构只约束系统区块；不为填充模板而编造信息，用户明确陈述优先于推断。

| 分区 | 系统区块的组织 | 状态 |
|---|---|---|
| General | 固定小节：基本信息、教育背景、个人偏好、当前状态、工作概况、健康概况、财务概况、目标概况、重要关系、其他。只写各方面的高层信息，不复制分区内容；姓名、生日、邮箱、住址等只在明确出现时写 | 已实现 |
| Work | 按项目 / 研究方向分小节；进展、〔决策〕、〔待解决〕写在条目里 | 已实现 |
| Health | 基本身体指标、健康关注、运动饮食习惯、重要变化；健康关注不得写成疾病诊断 | 阶段 2 |
| Finance | 收入、资产、投资、财务决策；金额必须带时间、币种和来源，否则不写 | 阶段 2 |
| Goals | 长期目标、计划、决策及变化原因 | 阶段 2 |

### 3.5 读取接口

`MemoryLibrary` 是统一的只读接口：`document(category)` 返回原文、用户手写部分（去掉系统区块）、系统条目（小节 / 来源 / kind）与修改时间；`daily(on:)` 读某天 daily；`search(query, in: categories)` 按分区全文检索。Memory Browser 与今后的 Memory API / MCP / Skill 都通过它读取，按分区授权。

### 3.6 旧布局迁移（Schema v1）

| 旧文件 | 迁入 |
|---|---|
| `summary.md` | `general.md`；小节映射：基本背景→基本信息、工作与研究→工作概况、习惯与偏好→个人偏好、长期目标→目标概况、重要关系→重要关系、其他→其他 |
| `work/**/*.md` | `work.md`，每个旧文件一个小节（小节名取旧文件的一级标题，重名时附路径） |
| `goals/`、`health/`、`finance/` 下的文件 | 对应单文件，规则同 work |

规则：

- 启动时、在同步与整理之前执行；失败时菜单提示，整理暂停，旧文件不动。
- 旧条目的文字、来源、kind（旧条目均为 unknown）原样搬入，不截断、不脱敏、不去标点；条目上限只用于之后的自动整理。
- 旧文件区块外的内容除系统骨架（一级标题、"## 记录"等生成标题）外，原样放到目标文件的"## 迁移自 <旧路径>"下。
- 写入后重读校验每条旧条目与每段用户内容都在；先保存迁移记录，再把旧文件复制到 `.archive/schema-v1/<旧路径>`，副本哈希一致后才删除原文件。归档里已有同名而内容不同的文件时另起名字，不覆盖。
- 幂等：再次运行不会重复写入；中途崩溃后再运行会从剩下的旧文件继续。只剩 `.DS_Store` 的旧目录在迁移后删除。
- 迁移记录：`.archive/schema-v1/migration.json`（源文件哈希与归档位置、目标文件迁移后的哈希；迁移前已存在的目标文件另存副本）。
- 回滚 `amai-memory migrate --rollback`：任一目标文件在迁移后被修改、归档副本缺失或哈希不符、原位置已有文件时整体拒绝；成功时旧文件复制回原位，新文件移到 `.archive/schema-v1-rollback/<时间>/`，不删除。回滚用于配合旧版 Amai，新版下次启动会再次迁移。`--status` 只读检查记录与归档完整性。

## 4. 写入规则

### 4.1 写入路径

```text
ActivitySegment ──► MemoryWriter.ingest
                      │
                      ├─ 总是：追加到 daily/<date>.md 的「时间线」
                      ├─ 条件：命中专题规则 → 写入专题文件「待澄清」或「进展记录」
                      └─ 从不：直接写 general.md
```

### 4.2 规则

1. **daily 全收但有过滤**：时间线收录所有非 idle 片段；连续同类片段合并；低置信度（< 阈值，待定）的片段只保留标题不保留摘要。
2. **专题需要触发条件**：例如同一项目在 N 天内出现 M 次、或片段被标记为"决策 / 计划"类；MVP 阶段触发规则保持简单、可解释、可配置。
3. **推断不升级**：`inf` 永远不会因为出现次数多而自动变成 `obs` 或 `confirmed`；升级需要用户动作（编辑 / 确认）。
4. **冲突处理**：新信息与已有条目冲突时，按 来源可信度（stated > confirmed > obs > inf）→ 时间（新优先）→ 置信度 排序；被覆盖的条目保留在 daily 中，专题文件记录变更而非删除（例如"原计划 X，10-19 改为 Y"）。
5. **去重**：同一来源片段只写一次；整理时对语义重复条目做合并（算法待设计，MVP 可先基于标题与时间范围的精确去重）。
6. **敏感内容**：MemoryWriter 不是最后防线，但要做二次检查：含密码 / 令牌 / 卡号模式的内容拒绝写入并计数记录。

7. ~~敏感专题走审批~~：已废止（ADR-0003 放弃审批流程；2026-11-03 用户确认 Health / Finance 允许自动写入，证据不足时不写，健康关注不得写成诊断，财务数据必须带时间、币种和来源）。
8. **常驻文件有预算**：整理写入单个目标（General 全文件、Work 的一个项目）有条目上限，超限由模型压缩；迁移不受此限。

### 4.3 写入原语

- 文件锁 + 写前重读 + 内容 hash 比对（检测用户外部编辑）→ 写临时文件 → 原子重命名。
- 读不出旧文件时拒绝写入，避免用空视图覆盖真实内容。
- 每次整理性改写保留前像快照（本地、可配置份数）。

### 4.4 禁止事项

- 不把 OCR 原文大段写入记忆。记忆是整理后的语义，不是原始数据的副本。
- 不在用户外部编辑期间覆盖文件（冲突时合并到新 section 并提示）。

## 5. 整理（Consolidation，M4 已实现，见 ADR-0003）

参考 OpenClaw：由 LLM 判断保存、更新、舍弃哪些内容；代码只负责安全。

| 任务 | 触发 | 输入 | 写入 |
|---|---|---|---|
| 日终摘要 | 凌晨 4 点后整理前一天（补整理最多 3 天）；菜单"整理今天" | 当天 daily 全文 + 代码计算的活跃与分类时长 | daily 中"## 摘要"下的 `amai:digest` 区块（时间线上方） |
| Work | 与日终摘要同一次 | 当天 daily + work.md 各项目的系统条目 | work.md 的 `amai:memory` 区块中对应项目的小节；其他项目不变；每天最多新建 3 个项目 |
| General | 每 7 天；首次在有 2 天摘要之后；设置"更新综合档案" | general.md 全文（用户手写部分作为已知事实）+ 最近 7 天摘要 + work.md 各项目 | general.md 的 `amai:memory` 区块，按推荐小节分组（§3.4） |

模型对每个目标返回**更新后的完整条目列表**（保留、合并、改写、舍弃由它决定）。条目格式见 §3.2；Schema v1 阶段 1 中模型输出的 kind 被忽略，新条目记为 inferred，已有条目沿用原 kind。Health / Finance / Goals 的整理与日终摘要附带的分类路由在阶段 2 实现。

代码保证：
- 只写系统区块，用户手写内容永不覆盖，并作为上下文交给模型。
- 来源日期：模型漏写时补当天；只保留合法日期。
- 去重：按规范化文本合并条目及其来源；同一天只正式整理一次（`index/consolidation.json`）；手动整理今天不影响凌晨的正式整理。
- 快照：改写前存旧版本到 `Application Support/Amai/snapshots/`（保留 100 份），`changes.jsonl` 记录每次改动。
- 防大量丢失：已有 4 条以上时，改写后少于一半则拒绝写入。
- 路径固定：模型只给项目名，文件路径由代码决定。
- 每个目标最多 40 条，每条最多 160 字，写入前凭据脱敏。

## 6. 检索（Retrieval）

### 6.1 接口

```text
retrieve(query: String, categories: [general | work | health | finance | goals | daily]?, timeRange?: , limit: Int)
  → [ { file, section, excerpt, score, kind, timestamp, sourceRefs } ]
```

### 6.2 实现策略（分阶段）

| 阶段 | 机制 | 说明 |
|---|---|---|
| MVP（已实现） | SQLite FTS5 trigram 分词，按 `##` section 建索引 + 分区（由文件路径决定）与日期过滤；不足 3 个字符的查询改用子串匹配 | 中文无空格，trigram 才能检索句中词；按文件修改时间与大小增量刷新，可全量重建；MVP 用 60 秒轮询纳入用户的外部编辑，未用文件事件 |
| 后续 | 加入本地 embedding 的语义检索，与全文检索混合排序 | 仅在全文检索明显不够时引入；embedding 模型本地运行 |
| 后续 | 检索结果按"稳定度"加权：general > 分区文件 > daily | 让回答优先使用整理过的信息 |

- 索引存放在应用内部目录，**不在记忆目录内**，可随时删除重建。
- 监听记忆目录文件变化（用户编辑）触发增量重索引。

## 7. 删除与修改

- 删除时间段：从 daily 时间线移除对应条目；分区文件与 general 中引用该时间段来源的条目标记为"来源已删除"，由下一次整理决定是否保留（若无其他来源则删除）。
- 删除单条：直接从文件移除并重索引。
- 用户在编辑器中直接改动：视为最高优先级，系统不回滚、不"纠正"。
- 所有删除同时清理 `extracted/` 中对应的派生数据与 `raw/` 中尚未过期的原始数据。

M3 已实现（检查器中的"删除时间段"与单个片段删除）：

| 操作 | raw/ | extracted/ | daily 区块 | 区块外手写内容 |
|---|---|---|---|---|
| 删除时间段 | 删除区间内的索引行；与区间重叠的视频分段整段删除（分段无法局部裁剪，宁可多删） | 删除与区间重叠的片段、其观察及区间内的其他观察 | 立即重渲染受影响的日期 | 不受影响 |
| 删除单个片段 | 不删除，按保留期清理 | 删除片段及其观察 | 立即重渲染当天 | 不受影响 |

分区文件与 general 的"来源已删除"处理在 M4 实现。

## 8. 隐私边界

- 记忆目录默认不被任何外部服务读取；整理 / 检索使用外部模型时，受全局外发开关控制，并在设置中明示"记忆内容会被发送"。
- 记忆文件不加密（用户可读是核心价值），依赖 macOS 用户目录权限与 FileVault；后续可考虑可选加密。

## 9. 参考与差异

详细研究见 [references/openclaw.md](references/openclaw.md) 与 [references/hermes.md](references/hermes.md)。本设计采纳的要点：

| 来源 | 采纳 | 体现在 |
|---|---|---|
| OpenClaw | 精选层（summary / 专题）与情景层（daily）之间的硬边界：daily 可自由追加但从不自动注入；summary 只能经门控整理写入 | 4.1 写入路径 |
| OpenClaw | 来源类别在写入时记录、存于 Markdown 之外的索引列，模型无法改写；晋升由结构性前提控制 | 3.2 标记 + 6 索引 |
| OpenClaw | 整理由确定性规则包裹模型判断（阈值、最大删除比例），每次改写可审计、可回滚 | 5 整理 |
| OpenClaw | 稳定事实原地取代而非追加矛盾条目；时间衰减只作用于 daily | 4.2 冲突处理、6.2 |
| Hermes | 常驻文件硬性字符预算，溢出由写入者整理 | 4.2 规则 8 |
| Hermes | 落盘前做凭据 / 注入模式扫描 | 4.2 规则 6 |
| Hermes | 锁 + 漂移检测 + 原子重命名；破坏性修改暂存审批并"钉住"条目 | 4.3、4.2 规则 7 |
| Hermes | 无人值守流程只能新增、不能改删 | 4.2 规则 7 |

刻意不采用：

- 两者默认依赖云端 embedding / provider。Amai 若引入向量检索，embedding 必须本地运行，远端只能显式开启。
- Hermes 的无时间戳、无来源、无整合模型；违反 Traceable / Consolidated。
- OpenClaw 的 cron / 插件框架 / 多渠道会话机制；Amai 用轻量后台任务实现整理。
- OpenClaw "按召回频率晋升"的思路有价值（被反复用到比模型觉得重要更可靠），但 Amai MVP 没有对话回合来产生召回信号，先作为后续整理策略的候选，待设计。

根本差异：它们的记忆来源是对话，Amai 的记忆来源是**被动感知的活动片段**。写入规则因此需要更强的过滤与"观察 / 推断"区分，这是 Amai 记忆层最重要的自有设计点。
