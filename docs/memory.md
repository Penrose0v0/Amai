# Amai 记忆系统设计

> 状态：草案（2026-10-19）。描述基于 Markdown 的长期记忆层：目录结构、文件格式、写入规则、检索与整理。整合 / 遗忘等算法细节标注为"待设计"，需与用户讨论后定稿，不由 Coding Agent 单方面决定。

## 1. 设计目标

| 目标 | 含义 |
|---|---|
| Markdown 为唯一真相 | 索引、缓存、向量都可以删掉重建；Markdown 丢了就是记忆丢了 |
| 人可读可编辑 | 用户用任何编辑器打开都能看懂、能改；系统尊重用户的修改 |
| 可追溯 | 每条有价值的记忆能回溯到时间与来源（哪一天、哪个活动片段） |
| 分层 | daily 是时间流水，专题是整合结果，summary 是稳定画像；三者信息密度递增、更新频率递减 |
| 不污染 | 推断不冒充事实；高频噪音不进专题与 summary |

## 2. 目录结构

```text
memory/
├── summary.md              用户综合档案（稳定信息）
├── daily/
│   └── YYYY-MM-DD.md       每日记录
├── health/
│   ├── sleep.md
│   ├── exercise.md
│   ├── nutrition.md
│   └── medical.md
├── work/
│   ├── research.md
│   ├── work-log.md
│   └── projects/
│       └── <project-slug>.md
├── finance/
│   ├── income.md
│   ├── expenses.md
│   ├── investments.md
│   └── assets.md
└── goals/
    ├── long-term.md
    ├── plans.md
    └── decisions.md
```

- 结构来自 AGENTS.md，是概念性初始结构；MVP 只会实际写入 `summary.md`、`daily/`、`work/`、`goals/`。health 与 finance 在感知数据能可靠支撑之前**不自动写入**，仅保留文件骨架供用户手写。
- 文件不存在时按需创建；用户删除某个专题文件视为"不想要这个专题"，系统不自动重建（待确认）。

## 3. 文件格式

### 3.1 通用约定

- 纯 Markdown，UTF-8，LF 换行。
- 顶部可选 YAML frontmatter，仅保存少量元数据（`updated`、`kind`），正文不依赖 frontmatter 也能阅读。
- 二级标题 `##` 作为可寻址的 section；系统按 section 更新，而不是整文件重写。
- 系统生成的条目带来源标记；用户手写的内容没有标记，系统视为 `stated`（用户陈述），**优先级高于推断**。

### 3.2 条目格式

每条系统写入的记忆是一个列表项或一个段落，尾部附带来源标记：

```markdown
- 下午集中在 Amai 架构文档上，主要修改 architecture.md 和 memory.md。 ⟨obs 14:05–16:20 · seg:2026-10-19-07⟩
- 似乎在评估 Swift 与 Rust 作为核心语言的取舍。 ⟨inf 0.6 · seg:2026-10-19-07⟩
```

标记含义：

| 标记 | kind | 说明 |
|---|---|---|
| `obs` | observed | 观察事实：OCR / 转录 / 焦点记录直接支持 |
| `inf <置信度>` | inferred | 模型推断 |
| `stated` | stated | 用户明确陈述（手写或未来通过对话确认） |
| `confirmed` | confirmed | 推断经用户确认后升级 |

`seg:` 指向抽取层的 ActivitySegment id，可据此在检查器中回看来源。具体标记语法（Unicode 括号 vs HTML 注释 vs 行尾 `<!-- -->`）待定；目标是对人阅读干扰最小、对机器可解析。

### 3.3 daily/YYYY-MM-DD.md

```markdown
---
updated: 2026-10-19T23:10:00+09:00
---
# 2026-10-19

## 摘要
一句到三句话的当日总览（整理时生成）。

## 时间线
- 09:30–10:15 阅读 Screenpipe 源码，关注 ScreenCaptureKit 用法 ⟨obs · seg:…⟩
- 10:15–12:00 …

## 工作
当日与工作 / 研究相关的要点。

## 状态与情绪
仅在有可靠依据时写入；默认留空。⟨inf⟩ 必须标注。

## 其他
```

时间线由 ActivitySegment 直接生成；其余 section 由日终整理生成。

### 3.4 专题文件（work/、goals/ 等）

```markdown
# 研究

## 当前方向
- …（stated / confirmed 优先）

## 进展记录
- 2026-10-19：…（整理时从 daily 提炼，附来源）

## 待澄清
- 系统推断但未确认的内容集中放在这里，便于用户一眼确认或删除
```

专题文件只接受**整理后的**信息，不接受逐段活动流水。

### 3.5 summary.md

```markdown
# 用户档案

## 基本背景
## 工作与研究
## 习惯与偏好
## 长期目标
## 重要关系
## 系统备注
（系统对自身理解的不确定性说明，如"以上关于作息的描述基于 3 天数据"）
```

写入门槛最高：只有跨多日重复出现、或用户陈述 / 确认的信息才进入。每个 section 有长度上限（待定，例如 30 行），超出时必须压缩而不是追加。

## 4. 写入规则

### 4.1 写入路径

```text
ActivitySegment ──► MemoryWriter.ingest
                      │
                      ├─ 总是：追加到 daily/<date>.md 的「时间线」
                      ├─ 条件：命中专题规则 → 写入专题文件「待澄清」或「进展记录」
                      └─ 从不：直接写 summary.md
```

### 4.2 规则

1. **daily 全收但有过滤**：时间线收录所有非 idle 片段；连续同类片段合并；低置信度（< 阈值，待定）的片段只保留标题不保留摘要。
2. **专题需要触发条件**：例如同一项目在 N 天内出现 M 次、或片段被标记为"决策 / 计划"类；MVP 阶段触发规则保持简单、可解释、可配置。
3. **推断不升级**：`inf` 永远不会因为出现次数多而自动变成 `obs` 或 `confirmed`；升级需要用户动作（编辑 / 确认）。
4. **冲突处理**：新信息与已有条目冲突时，按 来源可信度（stated > confirmed > obs > inf）→ 时间（新优先）→ 置信度 排序；被覆盖的条目保留在 daily 中，专题文件记录变更而非删除（例如"原计划 X，10-19 改为 Y"）。
5. **去重**：同一来源片段只写一次；整理时对语义重复条目做合并（算法待设计，MVP 可先基于标题与时间范围的精确去重）。
6. **敏感内容**：MemoryWriter 不是最后防线，但要做二次检查：含密码 / 令牌 / 卡号模式的内容拒绝写入并计数记录。

7. **敏感专题走审批**：对 `summary.md`、`health/`、`finance/` 的自动修改 / 删除默认暂存，由用户确认后应用；自动流程对这些文件只允许新增到「待澄清」。审批对象是暂存时看到的完整条目，若条目在审批前已被改动则拒绝应用。
8. **常驻文件有预算**：`summary.md` 每个 section 有字符上限；整理流程必须在预算内重写，超限即拒绝写入而不是截断注入。

### 4.3 写入原语

- 文件锁 + 写前重读 + 内容 hash 比对（检测用户外部编辑）→ 写临时文件 → 原子重命名。
- 读不出旧文件时拒绝写入，避免用空视图覆盖真实内容。
- 每次整理性改写保留前像快照（本地、可配置份数）。

### 4.4 禁止事项

- 不把 OCR 原文大段写入记忆。记忆是整理后的语义，不是原始数据的副本。
- 不在用户外部编辑期间覆盖文件（冲突时合并到新 section 并提示）。

## 5. 整理（Consolidation）

| 触发 | 动作 | 输出 |
|---|---|---|
| 日终（或次日首次启动） | 读取当日 daily 时间线 + 近期专题 → 生成当日摘要、工作要点；提取可进入专题的候选 | daily 的「摘要」「工作」section；专题文件「待澄清 / 进展记录」 |
| 每周 / 每 N 天 | 读取 daily 摘要 + 专题 → 检查 summary 是否需要更新 | summary.md 的差异化更新（只改变化的 section） |
| 用户手动 | 同上，立即执行 | 同上 |

- 整理通过 `ModelProvider` 调用模型，但 **prompt 的输入只包含记忆文件内容与片段摘要**，不包含原始截图 / 音频。
- 整理前后保留文件快照（本地、可配置份数），用于回滚。
- 整理的具体 prompt、合并策略、遗忘策略：**待设计**，需与用户讨论后定稿。

## 6. 检索（Retrieval）

### 6.1 接口

```text
retrieve(query: String, scope: [topic | daily | summary | all], timeRange?: , limit: Int)
  → [ { file, section, excerpt, score, kind, timestamp, sourceRefs } ]
```

### 6.2 实现策略（分阶段）

| 阶段 | 机制 | 说明 |
|---|---|---|
| MVP | 全文索引（按 section 粒度）+ 时间过滤 + 文件 / section 名称匹配 | 本地嵌入式数据库的全文检索即可；索引从 Markdown 增量重建 |
| 后续 | 加入本地 embedding 的语义检索，与全文检索混合排序 | 仅在全文检索明显不够时引入；embedding 模型本地运行 |
| 后续 | 检索结果按"稳定度"加权：summary > 专题 > daily | 让回答优先使用整理过的信息 |

- 索引存放在应用内部目录，**不在记忆目录内**，可随时删除重建。
- 监听记忆目录文件变化（用户编辑）触发增量重索引。

## 7. 删除与修改

- 删除时间段：从 daily 时间线移除对应条目；专题 / summary 中引用该时间段来源的条目标记为"来源已删除"，由下一次整理决定是否保留（若无其他来源则删除）。
- 删除单条：直接从文件移除并重索引。
- 用户在编辑器中直接改动：视为最高优先级，系统不回滚、不"纠正"。
- 所有删除同时清理 `extracted/` 中对应的派生数据与 `raw/` 中尚未过期的原始数据。

## 8. 隐私边界

- 记忆目录默认不被任何外部服务读取；整理 / 检索使用外部模型时，受全局外发开关控制，并在设置中明示"记忆内容会被发送"。
- 记忆文件不加密（用户可读是核心价值），依赖 macOS 用户目录权限与 FileVault；后续可考虑可选加密。

## 9. 参考与差异

详细研究见 [references/openclaw.md](references/openclaw.md) 与 [references/hermes.md](references/hermes.md)。本设计采纳的要点：

| 来源 | 采纳 | 体现在 |
|---|---|---|
| OpenClaw | 精选层（summary / 专题）与情景层（daily）之间的硬边界：daily 可自由追加但从不自动注入；summary 只能经门控整理写入 | 4.1 写入路径 |
| OpenClaw | 来源类别在写入时记录、存于 Markdown 之外的索引列，模型无法改写；晋升由结构性前提控制 | 3.2 标记 + 6 索引 |
| OpenClaw | 整理由确定性规则包裹模型判断（阈值、最大删除比例），每次改写可审计、可回滚 | 5 整理 |
| OpenClaw | 稳定事实原地取代而非追加矛盾条目；时间衰减只作用于 daily | 4.2 冲突处理、6.2 |
| Hermes | 常驻文件硬性字符预算，溢出由写入者整理 | 4.2 规则 8 |
| Hermes | 落盘前做凭据 / 注入模式扫描 | 4.2 规则 6 |
| Hermes | 锁 + 漂移检测 + 原子重命名；破坏性修改暂存审批并"钉住"条目 | 4.3、4.2 规则 7 |
| Hermes | 无人值守流程只能新增、不能改删 | 4.2 规则 7 |

刻意不采用：

- 两者默认依赖云端 embedding / provider。Amai 若引入向量检索，embedding 必须本地运行，远端只能显式开启。
- Hermes 的无时间戳、无来源、无整合模型；违反 Traceable / Consolidated。
- OpenClaw 的 cron / 插件框架 / 多渠道会话机制；Amai 用轻量后台任务实现整理。
- OpenClaw "按召回频率晋升"的思路有价值（被反复用到比模型觉得重要更可靠），但 Amai MVP 没有对话回合来产生召回信号，先作为后续整理策略的候选，待设计。

根本差异：它们的记忆来源是对话，Amai 的记忆来源是**被动感知的活动片段**。写入规则因此需要更强的过滤与"观察 / 推断"区分，这是 Amai 记忆层最重要的自有设计点。
